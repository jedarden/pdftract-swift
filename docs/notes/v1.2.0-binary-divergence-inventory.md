# SDK ↔ pdftract v1.2.0 binary divergence inventory

Probed 2026-11-24 against `pdftract-v1.2.0-x86_64-unknown-linux-musl`
(the release README "Binary version compatibility" links). This is the
executable-spec context for proposal pdfswift-ccccb2ff (the founding defect:
the generated API cannot drive the binary it was generated against). The
real-binary pins live in `Tests/PdftractTests/DocumentedApiConformanceTests.swift`;
this file is the full inventory, including methods outside those pins.

Reproduce: `docker run swift:5.10-jammy` (or any host with the musl release
binary) and run the SDK argv forms below against any small PDF.

## Per-method findings

| SDK method | Generated argv | Release-binary behavior |
|---|---|---|
| `extract` | `extract --json <input>` | exit 2 — `--json <PATH>` consumes the input as its output path, `<INPUT>` missing. Even with valid argv, the real `--json -` output has **no `schema_version`**, pages carry `index` (not `page_index`) and **no `width`/`height`/`rotation`** — `Document`/`Page` decode would fail. |
| `extractText` | `extract <input> --text --json` | exit 2 — "a value is required for '--text <PATH>'". The CLI's `--text` takes an output PATH (`-` = stdout). Even fixed, `--text -` emits plain text, not the `Document` JSON the SDK decodes. |
| `extractMarkdown` | `extract <input> --md --json` | exit 2 — same shape for `--md <PATH>`. Real `--md -` emits Markdown with `<a name="page-N"></a>` anchors and `---` page breaks. |
| `extractStream` | `extract --ndjson <input>` | **argv is the one that works** (exit 0), but `--ndjson` emits one *block* per line (`{bbox, block_index, kind, page, spans}`), not `Page` — every line fails `Page` decoding, so the stream yields **zero pages** silently (`onSkippedLine` is the only observer). All four `ExtractStreamConformanceTests` therefore have never passed against a real binary; they skip in every gate. |
| `search` | `grep <pattern> <input>` | exit 2 — **no `grep` subcommand exists** ("unrecognized subcommand 'grep'"). The argv divergence is pinned by `testSearchPinsTheCurrentGrepSubcommandDivergence`; because no binary can play grep at all, search's documented decode contract (zero-based `page`, `context.before`/`.after` surrounding text) is pinned against a fake grep child instead — `testSearchYieldsMatchesWithDocumentedPageAndContextFields`. |
| `getMetadata` | `extract --metadata-only --json <input>` | exit 2 — "unexpected argument '--metadata-only'". No such flag on the release binary's extract. |
| `hash` | `hash --json <input>` | exit 2 — "unexpected argument '--json'". Real `hash <input>` prints a bare `pdftract-v1:…` fingerprint line — not the `{hash, page_count, fast_hash, metadata}` `Fingerprint` JSON the SDK decodes. Two divergence layers. |
| `classify` | `classify --json <input>` | exit 2 — "unexpected argument '--json'" (classify's default output is already JSON; only `--pretty` exists). Behind that: the release binary gates classify itself behind the **'profiles' feature** — `classify <input>` exits **1** with `Error: Classification requires the 'profiles' feature to be enabled. Build pdftract with: --features profiles` (measured twice 2026-11-25, pdfswift-3307a377 probe; the 2026-11-24 probe recorded exit 0 — the two probes disagree on the exit, the error line and the feature gate agree). |
| `verifyReceipt` | `verify-receipt <pdf> <receipt> --json` | argv **aligns** — verify-receipt has a boolean `--json` and `<FILE.pdf> <RECEIPT.json>` positionals exactly as generated. End-to-end tested 2026-11-25 (pdfswift-302f0f7e, release tarball sha256 `f86d7274…`): a real receipt from `extract --receipts lite` **never verifies**. (Receipt production detail, corrected 2026-11-25 by the pdfswift-3307a377 probe: the STDOUT form `extract --receipts lite --json -` DOES attach receipts — span and block both carried `receipt` — contrary to the 2026-11-24 note that only the file-output form does; both forms work for producing a receipt.) `verify-receipt` recomputes a different PDF fingerprint than `extract` embeds (js-with-alerts: extract `cd0fe35a…` vs verify `28e01a73…`; valid-minimal: `ab24a95f…` vs other; tagged-suspects-true: extract `c5f1789d…`, hash `50a8d94f…`, verify `a682a012…` — three subcommands, three values), so every receipt dies at check 1: exit 10, `fingerprint_mismatch`, stdout JSON with `error`, stderr 0 bytes. SDK surface: throws `ReceiptVerifyError` (per `ExitCodeMappingTests`); never returns `valid:false`. Other verified exits: unknown receipt version → exit 1 pre-checks (stderr); patch-version diff → exit-path continues with stderr warning; missing receipt file → exit 1 with stderr. Exits 11/12 unobservable through real receipts (fingerprint gate short-circuits) — pinned by `ExitCodeMappingTests` + upstream verifier unit tests. |

## Source cases

- **`.path`** — passthrough as positional INPUT; correct.
- **`.url`** — URL string as positional INPUT (correct passthrough), but the
  release binary: rejects http(s) at the remote-feature gate (exit 2,
  "Remote sources require the 'remote' feature to be enabled. Build pdftract
  with: --features remote") before any network touch; rejects `file://` with
  exit 1 ("Failed to extract PDF: file://…" on the musl release; two local
  builds truncate the message). The README's headline
  `client.extract(.url(URL(string: "https://…")))` example is unreachable on
  the release binary.
- **`.bytes`** — spill + cleanup work (SourceBytesPassthroughTests pins the
  mechanics); through the one valid argv (`extract --ndjson`) the real child
  reads the spill (a 2-page PDF yields two NDJSON lines, exit 0) but every
  line fails `Page` decode (block-per-line shape above).

## Exit-code table divergences (README error table vs binary)

- Missing/unreadable local file: binary exits **1** ("Failed to extract
  PDF: <path>"), not 4 `SourceUnreachableError`.
- http(s) input without the remote feature: binary exits **2**, which the
  SDK maps to `CorruptPdfError`; the README lists exit 2 as "The PDF file is
  corrupt or invalid".

## Binary builds examined the same day

- `pdftract-v1.2.0-x86_64-unknown-linux-musl` — the only build that extracts;
  all findings above are its behavior.
- `~/.cargo/bin/pdftract` (2026-08-25 local build) and the a2ed4c96-lineage
  release build (2026-11-24) — identical clap-level argv rejections, but both
  fail every actual extraction (`Error: Failed to extract PDF`, exit 1) on
  inputs the musl release extracts, including the committed probe fixture
  `docs/notes/probes/fixtures/mini.pdf`. The pins in
  DocumentedApiConformanceTests assert only what the release binary is known
  to do.

## The executable gate over this inventory

`scripts/e2e-binary-verification.sh` (bead pdfswift-3307a377, 2026-11-25) is
this inventory in runnable form: it downloads the pinned release from the
public GitHub mirror (the README's own URL; Forgejo gates release attachments
behind sign-in, so the anonymous consumer path is the mirror), verifies the
tarball against the published `SHA256SUMS`, and runs the full suite in the
`swift:5.10-jammy` image with the binary mounted onto PATH. It fails on any
test failure OR any skip — the zero-skip rule closes the loophole where a
broken download degrades every binary-gated suite into its XCTSkip guard and
the run "passes" having exercised nothing. First full run: 2026-11-25, green,
against `pdftract-v1.2.0-x86_64-unknown-linux-musl` (sha256 `f86d7274…`).

Executable pins added the same day (this file's tables, now assertable):

- `ExtractStreamConformanceTests` — the three documented-contract tests that
  had never passed against any real binary are reality pins now
  (stream yields zero pages from block-per-line NDJSON; the buffered
  `extract` argv dies in clap on the same input), each with the documented
  assertion preserved in its flip note. The zero-page-PDF contract test held
  as written and stayed a contract test.
- `DocumentedApiConformanceTests` — `getMetadata` argv pin (exit 2,
  "unexpected argument '--metadata-only'") and the verifyReceipt pair: the
  end-to-end SDK→binary→SDK pin (argv conforms, real receipt from
  `extract --receipts lite`, exit 10 → `ReceiptVerifyError`) and the decode
  twin proving the REAL `verify-receipt --json` stdout parses into
  `ReceiptVerificationResult` (`status`/`best_iou`/
  `expected_content_hash`/`actual_content_hash`/`error` — the only
  operation whose real wire output this SDK decodes today).
- Serialization twins for the buffered `--json -` output: the `metadata`
  member decodes into the SDK's `Metadata` (`page_count` is the one required
  key; the rest optional), the `Block`/`Span` leaves decode (the SDK's leaf
  fields are a strict subset of the binary's members), and the whole thing
  cannot decode as `Document` (keyNotFound `schema_version` first — the
  binary's pages carry `index`, not `page_index`, and lack
  `width`/`height`/`rotation`). So the buffered path's drift is exactly one
  wrapper layer deep: argv + page/schema wrapper, not the leaves.
