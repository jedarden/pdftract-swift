# SDK ↔ pdftract v1.2.0 binary divergence inventory

Probed 2026-11-24 against `pdftract-v1.2.0-x86_64-unknown-linux-musl`
(the release README "Binary version compatibility" links). This is the
executable-spec context for proposal pdfswift-ccccb2ff (the founding defect:
the generated API cannot drive the binary it was generated against). The
real-binary pins live in `Tests/PdftractTests/DocumentedApiConformanceTests.swift`;
this file is the full inventory, including methods outside those pins.

Reproduce: `docker run swift:5.10-jammy` (or any host with the musl release
binary) and run the SDK argv forms below against any small PDF.

## Per-method findings

| SDK method | Generated argv | Release-binary behavior |
|---|---|---|
| `extract` | `extract --json <input>` | exit 2 — `--json <PATH>` consumes the input as its output path, `<INPUT>` missing. Even with valid argv, the real `--json -` output has **no `schema_version`**, pages carry `index` (not `page_index`) and **no `width`/`height`/`rotation`** — `Document`/`Page` decode would fail. |
| `extractText` | `extract <input> --text --json` | exit 2 — "a value is required for '--text <PATH>'". The CLI's `--text` takes an output PATH (`-` = stdout). Even fixed, `--text -` emits plain text, not the `Document` JSON the SDK decodes. |
| `extractMarkdown` | `extract <input> --md --json` | exit 2 — same shape for `--md <PATH>`. Real `--md -` emits Markdown with `<a name="page-N"></a>` anchors and `---` page breaks. |
| `extractStream` | `extract --ndjson <input>` | **argv is the one that works** (exit 0), but `--ndjson` emits one *block* per line (`{bbox, block_index, kind, page, spans}`), not `Page` — every line fails `Page` decoding, so the stream yields **zero pages** silently (`onSkippedLine` is the only observer). All four `ExtractStreamConformanceTests` therefore have never passed against a real binary; they skip in every gate. |
| `search` | `grep <pattern> <input>` | exit 2 — **no `grep` subcommand exists** ("unrecognized subcommand 'grep'"). |
| `getMetadata` | `extract --metadata-only --json <input>` | exit 2 — "unexpected argument '--metadata-only'". No such flag on the release binary's extract. |
| `hash` | `hash --json <input>` | exit 2 — "unexpected argument '--json'". Real `hash <input>` prints a bare `pdftract-v1:…` fingerprint line — not the `{hash, page_count, fast_hash, metadata}` `Fingerprint` JSON the SDK decodes. Two divergence layers. |
| `classify` | `classify --json <input>` | exit 2 — "unexpected argument '--json'" (classify's default output is already JSON; only `--pretty` exists). Behind that: the release binary gates classify itself behind the **'profiles' feature** — `classify <input>` exits **0** with `Error: Classification requires the 'profiles' feature to be enabled`. |
| `verifyReceipt` | `verify-receipt <pdf> <receipt> --json` | argv **aligns** — verify-receipt has a boolean `--json` and `<FILE.pdf> <RECEIPT.json>` positionals exactly as generated. Result decode untested (needs a real receipt from `--receipts lite`). |

## Source cases

- **`.path`** — passthrough as positional INPUT; correct.
- **`.url`** — URL string as positional INPUT (correct passthrough), but the
  release binary: rejects http(s) at the remote-feature gate (exit 2,
  "Remote sources require the 'remote' feature to be enabled. Build pdftract
  with: --features remote") before any network touch; rejects `file://` with
  exit 1 ("Failed to extract PDF: file://…" on the musl release; two local
  builds truncate the message). The README's headline
  `client.extract(.url(URL(string: "https://…")))` example is unreachable on
  the release binary.
- **`.bytes`** — spill + cleanup work (SourceBytesPassthroughTests pins the
  mechanics); through the one valid argv (`extract --ndjson`) the real child
  reads the spill (a 2-page PDF yields two NDJSON lines, exit 0) but every
  line fails `Page` decode (block-per-line shape above).

## Exit-code table divergences (README error table vs binary)

- Missing/unreadable local file: binary exits **1** ("Failed to extract
  PDF: <path>"), not 4 `SourceUnreachableError`.
- http(s) input without the remote feature: binary exits **2**, which the
  SDK maps to `CorruptPdfError`; the README lists exit 2 as "The PDF file is
  corrupt or invalid".

## Binary builds examined the same day

- `pdftract-v1.2.0-x86_64-unknown-linux-musl` — the only build that extracts;
  all findings above are its behavior.
- `~/.cargo/bin/pdftract` (2026-08-25 local build) and the a2ed4c96-lineage
  release build (2026-11-24) — identical clap-level argv rejections, but both
  fail every actual extraction (`Error: Failed to extract PDF`, exit 1) on
  inputs the musl release extracts, including the committed probe fixture
  `docs/notes/probes/fixtures/mini.pdf`. The pins in
  DocumentedApiConformanceTests assert only what the release binary is known
  to do.
